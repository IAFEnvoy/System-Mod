# 客户端物品检索

物品查询、系统商城、物品收购和抽奖的页面搜索，以及系统输入框中的 `/item`、`/shop`、`/buyback`、`/lottery`、`/recipe` 和按名称取出空间内容的请求，先使用客户端原版 `SearchTree<ItemStack>` 查找候选，再交给服务端筛选和处理。客户端只提供候选物品，不提供价格、奖励或执行权限。

## 搜索内容

- 普通查询使用原版物品 tooltip 搜索树，匹配当前客户端语言下的名称、提示文字和注册 ID；资源包翻译与模组添加的 tooltip 随原版索引生效。
- `#标签` 使用原版标签搜索树，例如 `#minecraft:planks`。
- 完整注册 ID 只保留该物品类型，但同一 ID 下的药水、附魔书等组件变体仍可分别出现。
- 候选来源是原版创造模式搜索集合，不保证收录未加入该集合的隐藏物品；不能自动搜索未加载的其他语言，也不会枚举背包中所有自定义组件组合。
- 系统空间已有快照时，单独使用实际存储物品建立原版 tooltip／标签搜索树，能检索改名、附魔等组件变体，不把系统币等内容的物品图标当成可取出的物品。快照更新会重建该索引；尚未查询过空间时使用创造搜索集合提供候选。

原版索引在后台构建，界面不会同步等待索引完成。切换连接、重载资源或同步标签会清除本模组的索引状态；语言变化后使用更新后的原版索引。尚未打开过创造模式界面的生存玩家也能搜索。

自然语言由服务端路由后发起的查询、AI 工具调用及其他没有客户端候选的服务端请求，仍使用注册 ID／服务端名称的备用检索；不会伪造客户端的 tooltip 结果。

## 其他入口

| 入口 | 行为 |
| --- | --- |
| 抽奖页面／`/lottery 锋利` | 匹配奖池名称／ID，或池内任意奖励中的实际物品及组件；不限于目录 tooltip 预览的十种奖品。匹配不改变奖池、概率、次数限制和费用。 |
| `/recipe 钻石镐`、`/recipe iron ingot loot` | 接受名称、tooltip、ID 或标签；唯一物品类型直接查来源，多个类型显示物品选择卡。来源按物品类型查询，同一 ID 的组件变体合成一个选项。末尾范围仍支持 `all`／已注册 Provider；完整 ID 的未知范围会被拒绝。 |
| `取出十个铁锭`／`/take a stack of iron ingot` | 精确匹配本地空间条目时直接发送条目 ID，其余使用搜索候选。服务端只与本人当前可用的真实内容匹配，多个条目或候选批次未读完时返回空间列表提示选择，不猜测取出目标。 |

空间取出保留原有数量／一组语义；点击选择仍由服务端重新核对归属、状态和实际可用数量，附件中的物品永远不会直接入库或发给玩家。

## 有界批次与卡片

每次最多上传 32 个候选；候选保留完整 `ItemStack` 组件，传输时使用不可变的 `ItemStackTemplate`，数量统一为 1。每个堆叠的二进制编码最多 4 KiB，一批堆叠最多 24 KiB。单次最多检查 256 个原版匹配项，超大或无法编码的堆叠跳过，避免异常条目导致无限扫描。

未读完时，物品卡片显示「更多物品」，商城／收购卡片显示「继续搜索」，点击后才上传下一批。卡片网格内部的上／下页只切换当前批次，不发请求。商城仍最多显示 128 个合并条目；即使本批候选全部被服务端过滤，只要还有原版匹配项，就保留继续搜索入口。

抽奖区分「奖池批次」与「物品候选批次」：原有上／下一批奖池按钮复用同一份服务端搜索引用，「继续搜索」才收集下一批物品并从该批奖池的第一页开始。空匹配批次也保留继续搜索按钮，避免查不到后面的奖品。来源选择卡继续搜索时保留原查询范围。

多结果中的物品详情使用服务端签发的搜索引用及批内索引，保留原候选组件，不退化为只按物品 ID 重建默认堆叠。物品来源查询仍按物品类型检索配方、掉落与标签。

## 服务端校验与交易

服务端检查请求类型、查询词、游标、候选数量、重复项、堆叠数量、组件合法性、注册物品及当前世界功能开关。二进制解码前先限制每个堆叠及批次的字节数。客户端本地匹配本身不作为权限证明，客户端语言和 tooltip 也不在服务端重新执行。

无限交易额外检查组件变体来源：默认组件允许进入估值；非默认组件必须是 Evaluate 在服务端已知的精确物品／组件组合，收购也允许玩家背包里实际持有的相同组合。仅有通配估值不能让客户端凭空创造可购买的自定义组件。准入与排除 matcher、P90、固定库存优先、条件和当前估值继续由服务端执行；收购精确消耗报价对应的完整组件变体。

生成商品的 ID 关联服务端保存的堆叠选择器；客户端不能用 ID 拼接任意物品或价格。报价及付款重新解析选择器并复核当前规则，报价保留原有两分钟有效期。固定商品仍可按条目名称／ID 搜索，也会匹配客户端候选对应的奖励物品或收购物品。

搜索引用与生成选择器均按玩家隔离、五分钟过期，退出或权限变化时清除，不写入存档。搜索批次最多每玩家 8 份／全服 128 份，生成选择器最多每玩家 256 份／全服 2048 份；过期或被淘汰的旧卡片需重新搜索。缓存只保存候选及选择器，不保存可信价格。

## 开发入口

| 入口 | 职责 |
| --- | --- |
| `module.client.ClientItemSearchCache` | 初始化原版搜索集合，异步等待索引，生成有界候选批次。 |
| `module.client.ClientItemSearch` | 从结构化查询或原卡片事件提取只读检索条件，保留卡片关联。 |
| `data.item.ItemSearchQuery` / `ItemSearchBatch` | 查询接口与带组件、长度受限的二进制附件。 |
| `assistant.item.ItemSearches` / `ServerItemSearchCache` | 校验候选、签发玩家引用、维护有限缓存与组件选择器。 |
| `assistant.commerce.ShopRequest` | 将已验证候选传给当前启用的商城来源。 |

网络协议已升为 `3`，客户端与服务端必须一起更新。普通动作继续使用原注册类型；大块组件数据通过请求包的可选二进制附件传递，不塞进按钮字符串或模型 schema。
