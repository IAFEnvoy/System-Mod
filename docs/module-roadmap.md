# 模块全量清单与推荐优先级

整理日期：2026-11-15。实现基线：当前 `master`（Minecraft 26.1.2）工作区源码，包含尚未提交的修改。本文件是后续开发目录，不是发布版本的功能承诺，也不代表 1.21.1 已同步。

本清单完整覆盖[系统文功能调研](../research/system-novel-functions.md)中的 **22 类玩法、149 个细项**，另外列出建议独立落地的“收藏图鉴”，共 **23 类玩法候选**；经济、仓储、关系、卡片等基础能力另列。这里的“完整”指覆盖此次调研及当前项目能力，不表示穷尽所有小说和模组的设定。

原调研的来源编号、原文核验范围和 32 项“延伸”标记仍以原文件为准。下文的实现状态、模块划分和优先级是对本仓库的开发评估，不作为新增的原著设定证据。本次只阅读源码和文档，未启动游戏验收。

## 阅读方式

| 标记 | 含义 |
| --- | --- |
| ✅ 已实现 | 当前代码已经接入所列范围；不表示所属大类的所有设想都已实现。 |
| 🟡 部分实现 | 已有可用子集或联动，但表中列出的剩余流程仍需开发。 |
| 🧩 可配置 | 现有能力可以承载此类内容，仍需编写数据或接入具体事件；不算已有完整玩法。 |
| ⬜ 未实现 | 尚无对应完整业务流程；现有工具、action 或展示节点不能代替该流程。 |

| 优先级 | 建议 |
| --- | --- |
| P0 | 为选定玩法补必要的通用支撑，先于依赖它的扩展实施；按需要补，避免先造大框架。 |
| P1 | 优先开发：现有服务复用多、玩家收益明确、首版边界易收敛。 |
| P2 | 下一阶段：需要新的记录或规则，但能形成规模适中的完整流程。 |
| P3 | 中长期：涉及新的成长、对象或多人协作体系，宜分阶段实现。 |
| P4 | 可选大型方向：世界模拟、实体 AI、领地或跨服事务等，应先确认产品目标。 |
| 维护 | 当前范围已有，继续修复与完善；不计入新增功能排期。 |

下文的优先级针对“下一步增量”，不是要求重做已有功能。工作量用“小／中／大／很大”作相对比较，不承诺具体工期。服务端负责真实数据、条件、扣费、结算与持久化；客户端负责展示和输入，AI 只提出操作意图，不能成为奖励、价格或完成状态的事实来源。

| M16 | 事业经营 | ⬜ 当前商城是系统售货，不是玩家经营账本。 | 先做一个抽象店铺：产品、收入支出、周期结算。 | P3 | 大；独立账户、有效交易、周期账本。 |
| M17 | 组织经营 | ⬜ 无组织成员、职位、共享目标与设施状态。 | 先成员／权限／贡献账户，再接组织商城和目标。 | P3 | 大；共享存储、成员权限、多人并发。 |
| M18 | 领地与军团 | ⬜ 无区域、建筑、生产或军队运行时。 | 若确定做，先做数据化设施升级和资源结算，实体军团最后做。 | P4 | 很大；区域归属、设施、单位、多人冲突。 |

| M20 | 模拟与推演 | ⬜ 自由聊天不是有状态、可结算的模拟器。 | 先做纯数据、有限回合的事件推演；有可信模型后再谈战斗或人生模拟。 | P4 | 很大；状态转移、随机种子、结果可验证性、结算隔离。 |
| M21 | 世界探索与传送 | ⬜ 没有锚点名册、解锁和传送流程。 | **先传送锚点**：固定坐标／维度、费用、条件、安全落点。跨服和新世界后置。 | P2；跨服 P4 | 中；服务端校验、维度可用性、落点与冷却。 |
| M22 | 交易市场 | ⬜ 当前商城没有卖方、托管、玩家交易或竞价。 | 先固定价格的玩家物品挂牌，再考虑拍卖和服务订单。 | P3；跨服 P4 | 大到很大；托管、交付、撤单、离线卖家、恢复账本。 |
| M23 | 收藏图鉴 | ⬜ 物品查询和 FTBQ 记录不能代替 System 的收藏登记。由原“收藏／系列成就”中拆出的候选。 | **背包手动登记、系列进度、阶段奖励与已领取状态**；先不消耗物品。 | **P1** | 中；收集定义、玩家历史、领奖；共享成就事件与记录。 |

M23 可以独立启用，但收藏达成只向 M05 提供事件，不再维护第二套成就裁决。图纸、功法、灵兽、人物等奖励类型属于内容及结果适配，不应按奖励名称拆成许多同质模块。

## 二、当前已实现的模块与基础能力

### 正式服务端模块

以下是当前 `SystemServerModules` 注册的 **15 个类型 ID**，不是某个数据包中的实例 ID。类型放在 `system:server_module`，带参数实例放在 `system:system_module`，系统定义引用实例或其 tag。

| 类型 ID | 状态 | 当前职责与边界 |
| --- | --- | --- |
| `system:core` | ✅ | 核心工作流、基础请求和工具装配；不视为一个新玩法。 |
| `system:binding` | ✅ | 系统绑定、解除、模块启停与相关入口；当前一个玩家最多绑定一个系统。 |
| `system:usage` | ✅ | 用量查询及展示；不是游戏内经济账户。 |
| `system:player` | ✅ | 玩家信息快照与卡片；不是自建等级、资质或技能模型。 |
| `system:items` | ✅ | 物品查询、实际主手鉴定、获取来源；见 M09。 |
| `system:economy` | ✅ | 多币种钱包、管理员调整、系统币支付、货币 action／condition。 |
| `system:workshop` | ✅ | 报价后维修主手装备；见 M12。 |
| `system:online_jobs` | ✅ | 在线作业定义、计时、暂停与领取；见 M08。 |
| `system:signin` | ✅ | 每日签到工作流和物品奖励；见 M02。 |
| `system:inbox` | ✅ | 待领取物品奖励与交付；不是可存入的随身仓库。 |
| `system:shop` | ✅ | 系统商品购买与限购；见 M04。 |
| `system:lottery` | ✅ | 加权单抽与物品奖励；见 M03。 |
| `system:advancement` | ✅ | 原版成就触发工作流；完整成就玩法仍为 M05 的待扩展范围。 |
| `system:ftb_quests` | ✅ 可选联动 | 任务查询与操作、通知、固定、说明书检索；仅安装对应依赖时启用。 |
| `system:web_search` | ✅ 可选工具 | 搜索与网页提取、授权与计费；不自动赋予联网权限。 |

| 通知、历史和常驻 HUD | ✅ | 交互通知、历史消息、固定卡片、HUD 编辑、进出动画与显示策略。 |
| Emotion | ✅ | 数据驱动表情、熊猫头 HUD、客户端调试状态、服务端覆盖、说话偏移与贴图回退；不采集真实情绪，不维护好感度。 |
| 经济账户 | ✅ | 多种非负整数余额、服务端命令与支付；玩家转账、自动兑换、受限经营资金未接入。 |
| 奖励交付 | 🟡 | 当前 `Reward` 是标题和 **1～36 项物品模板**；没有通用货币、经验、技能、实体等奖励分派。 |
| 报价与事务 | 🟡 | 现有商品／抽奖订单、限购占额和维修校验可以复用经验；不代表已有任意跨账户交易事务框架。 |

### 应优先补的共用增量

只有选定玩法需要时才实施。不要为了下表先改造所有已稳定的流程。

| 增量 | 当前状态 | 为什么需要／首版边界 | 优先级 |
| --- | --- | --- | --- |
| 非物品奖励结果 | 🟡 物品已通，其他未通 | 回收得系统币、等级得经验、研究解锁都需要确定性的结果执行。先接货币，再接真正使用到的类型；不能仅有 Saturn action 就宣称商城、抽奖、签到已经支持。 | P0，按需求 |
| 领取幂等与恢复 | 🟡 现有业务各有记录 | 新增里程碑、图鉴领奖和返还时明确已生成／待领取／已领取，防重复点击与中断重发；优先复用合适的已有交付。 | P0，按需求 |
| 日期／周期语义 | 🟡 每日签到、周期限购已有 | 连签、轮换和结算明确时区、日／周边界、错过重置、补签、配置变化；提取共用部分即可。 | P0～P1 |
| 事实事件与累计记录 | 🟡 模块生命周期和现有事件已有 | 收藏登记、首次、系列和行为统计都需要事实来源、唯一键与去重；先覆盖当前玩法事件。 | P1 |
| 内容条件／效果接入 | 🟡 Saturn 与部分业务已有 | 为新条目明确哪里支持 condition／action，不假设任意现有商品和奖励都已支持。 | P1～P2 |
| 关系／权限服务 | ⬜ 只有系统与 AI 权限等现成部分 | 仅在组织、随从、师徒等落地时建立对象关系和成员权限；不把 OP 当全部业务身份。 | P3 |
| 托管与跨玩家结算 | ⬜ | 市场／委托先锁定标的，再付款与交付，需处理离线、撤单、失败恢复；不能直接拿系统售货订单冒充。 | P3 |

## 三、原调研 149 项逐项落地表

编号用于检查覆盖和追踪，不是注册 ID。每个表中的“下一步”同时说明介绍、当前限制或建议归属；优先级只针对尚未完成部分。

## 四、推荐开发顺序与首版验收边界

### 第一批：收藏、回收与签到增量

| 顺序 | 项目 | 首版必须完成 | 首版暂缓 |
| --- | --- | --- | --- |
| 1 | 收藏图鉴 | 数据包定义系列、条目匹配和阈值；玩家背包手动登记；登记不消耗物品；显示进度和领取状态；重登保留；已领取奖励不会重复发。 | 全量物品自动监听、任意组件判定、跨服收藏、复杂图鉴搜索。 |
| 2 | 工坊回收／分解 | 数据定义输入和结果；先选择明确物品或主手；服务端报价并复核；扣除一次、结果一次；物品结果进收件箱；若提供币种结果则补上对应持久结算。 | 自动回收背包、持续扫描、随机多级分解、装备价值 AI 估价。 |
| 3 | 签到里程碑 | 累计／连续分开记录；定义日期与断签规则；7 天等阈值独立领奖；固定规则奖励路径；每日奖励与里程碑各自防重复。 | 付费补签、追溯老数据、跨服连续签到、复杂活动日历。 |

这一批可复用现有物品奖励，不必为了图鉴和签到先实现所有奖励类型。**系统币回收**确实需要新增货币产出／交付接入，应在该功能前补齐，不能只在 JSON 中写一个未支持字段。

## 五、后续实现应保持的边界

1. **模块按流程划分，数据按内容划分。** 奖池抽到灵兽／图纸／技能不是三个抽奖模块；不同币种不是多个经济模块；失败惩罚和返还倍率属于规则。
2. **先复用，再新增类型。** 维修、回收和分解优先扩展工坊；普通物品兑换优先用商城；收藏为成就提供事件；不要复制 FTBQ 的完整任务系统。
3. **数据驱动不等于任意字段都有效。** 当前正式数据包注册表为 `emotion`、`currency`、`online_job`、`system_module`、`system`、`signin_reward`、`shop_offer`、`lottery_pool`。图鉴、研究、锚点等是候选，本文没有为其注册新 ID；将来新增注册表使用单数。
4. **结果必须服务端确定且可恢复。** 物品、系统币、经验、能力授予分别明确执行与交付语义；扣费前后要有可追踪状态，不能依赖客户端已显示某个卡片判断成功。
5. **AI 与联网保持可选。** 尽可能让玩法具有离线入口和确定性规则，AI 负责路由、说明与表达。网页工具维持“启用模块且本次明确允许”的规则；查询先使用有权限访问的本地知识。
6. **可选联动不污染必装数据。** FTBQ、宠物、技能、经济提供方等未安装时，不加载其类、不注册对应实现，也不让必须加载的内置定义引用缺失类型。
7. **存储按对象归属。** 玩家收藏、签到、作业放对应模块 DataStorage；世界首达和组织共享数据放适当的存档共享服务；知识数据库不承担所有经济事务。
8. **新功能同时提供可用交互。** 明确卡片、模块入口、界面内指令、工具入口、权限和双语文本；不能只有工具定义或只有一张空卡片就标记完成。
