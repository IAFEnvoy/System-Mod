# 每日签到与本地进度评估

发布签到池只提供少量基础物资；首次／累计签到奖币由成就承担，模块保留连续 7 天里程碑。具体默认量见[发布默认数据](release-data.md)，下文配置结构和 Codec 缺省值可由整合包自行覆盖。

签到仍从数据包 `system:signin_reward` 注册表中选择一个完整奖励包，不临时生成物品，也不按估值修改奖励数量。离线与 AI 两条路径共用日期、每日唯一标记、奖励快照和系统空间交付；切换模式不能重复签到。

在系统界面输入 `/signin`、`签到` 或点击签到按钮执行；`/signin_status` 只查询状态，不领取当天权益。业务日使用服务端 `system-agent.json` 的 `timeZone`，默认 `Asia/Shanghai`。

## 选择路径

| 当前生效模式 | 奖励选择 |
| --- | --- |
| 模块配置了非空 `rules.daily_cycle`，任意模式 | 按玩家成功签到总次数轮换固定奖励；无需 AI 或 Evaluate 筛选，仍核验奖励可选项和条件 |
| 离线，包括缺少模型密钥或管理员禁用 AI 后的生效模式 | Evaluate 估值 → 玩家进度分位数 → 数据包奖励包筛选 → 本地选择；不请求模型或网络 |
| 标准、扩展、自由 | 保留 AI 从服务端批准的候选包中选择的流程，沿用模型预算、权限和用量统计 |

AI 请求失败不会自动转成本地随机奖励。需要本地路径时切换离线模式。明确的签到指令、按钮及有限的完整签到短语可以本地直达；模糊的写操作仍使用候选操作或 AI 路由，不降低通用写入权限检查。

## 模块配置

文件示例：`data/example/system/system_module/signin.json`。

```json
{
  "server": {
    "type": "system:signin",
    "rewards": "#system:default",
    "offline": {
      "percentile": 0.9,
      "lower_factor": 0.8,
      "upper_factor": 1.3,
      "recipes": true
    }
  },
  "client": "system:signin"
}
```

| `server` 字段 | 类型 | 默认值 | 说明 |
| --- | --- | --- | --- |
| `rewards` | 奖励 ID、`#tag` 或混合数组 | 全部有效奖励 | 沿用模块目录可选项；内置模块显式使用 `#system:default` |
| `offline` | 对象 | 使用下列默认值 | 本地进度评估与奖励筛选参数 |
| `offline.percentile` | 数字，0.5～0.99 | `0.9` | 进度分位数；可设 `0.95` 使用 P95 |
| `offline.lower_factor` | 有限正数 | `0.8` | 优先奖励包总价值的下界比例 |
| `offline.upper_factor` | 有限正数 | `1.3` | 奖励包总价值的上界比例，不因缺少候选自动扩大 |
| `offline.recipes` | 布尔 | `true` | 将已解锁配方的静态物品产物并入样本 |

`lower_factor` 不能大于 `upper_factor`。定义和目录都是数据包注册表，修改后需要重新进入世界或重启服务器；Evaluate 自身价值更新后，下次查询使用其最新快照。

## 进度样本与分位数

`assistant.progression.PlayerProgression` 是独立于签到的服务端评估入口，结果为 `ProgressionEstimate`，包含核心价值、奖励区间、硬性下界、样本数、配方补充样本数、分位数和置信等级。

1. 读取玩家当前背包、装备与副手，以及可选的已解锁配方产物；特殊配方、动态或无法识别的产物显示不作为样本。
2. 用 Evaluate 查询实际物品及组件的**单件价值**。未知、非有限或非正价值忽略。
3. 按物品与组件补丁去重，不按堆叠数量加权；相同物品在背包和配方中出现多次只计一次，不同组件变体可分别计数。
4. 将价值升序排序，取 `floor((n - 1) × percentile)` 下标处的值。使用向下的经验分位数，避免小样本插值混入单个极端高值。
5. 有效变体不足两种时不据此建立进度档位，原始评估记为零；若阶段校准也未提供正的进度下界，使用冷启动选择，在阶段限制内选择价值最低的可用奖励包。

例如九种价值 50 的普通物品和一种价值 10000 的偶然掉落，P90 为 50。堆叠 64 个相同物品不会增加该种物品的样本权重。这里只观察当前实物与已解锁配方，不保存“曾经获得过”的物品历史；已解锁也不代表现在能合成，整合包批量解锁全部配方时可关闭 `recipes`。

默认优先区间为 `[P90 × 0.8, P90 × 1.3]`，并受扩展提供的阶段上下界钳制。无阶段校准时只依据价值分布。置信等级是样本量与是否校准的提示，**不是统计概率**：P90 少于 10 个有效变体、P95 少于 20 个为低；样本足够但无校准为中；样本足够且存在校准为高。

只在查询签到状态或执行签到时评估，不逐 tick 扫描，不保存跨重载的物品价值缓存。Evaluate 查询和配方读取调度到服务端游戏线程，玩家文件事务仍留在工作线程，避免持有存储锁等待游戏线程。

## 奖励包估值与筛选

奖励包总价值等于 `items` 与物品型 `contents` 中各物品的单件 Evaluate 价值乘数量后求和。含未知物品、系统币、经验或 Saturn action 等无法自动估值的内容时，整个包默认不进入离线候选；可以声明 `offline_value`。

文件示例：`data/example/system/signin_reward/experience.json`。

```json
{
  "label": { "text": "基础经验补给" },
  "offline_value": 24,
  "contents": [
    {
      "content": { "type": "system:experience" },
      "amount": 30
    }
  ]
}
```

| 奖励字段 | 类型 | 默认值 | 说明 |
| --- | --- | --- | --- |
| `offline_value` | 有限正数 | 按物品自动求和 | 覆盖**整个包**的离线价值，包括其中全部物品和非物品内容；不是单件价格，也不是系统币汇率 |

其他奖励字段与[奖励结果](rewards.md)、[条目条件](catalog-conditions.md)相同。把新奖励加入模块允许的 tag 或 ID 列表后才可使用；不应为了通过筛选随意低报高价值包的价值。

筛选先应用模块可选项、`enabled`、`display_condition` 和 `condition`，再排除低于阶段硬性下界或高于价值上界的包。优先保留完整区间内的包；若区间内没有候选，只选择上界以内、最接近区间的较低价值包，不突破阶段硬性下界。冷启动则选允许范围内的最低价值包。剩余多个候选时按玩家 UUID 和业务日期固定种子选择。

没有可用包时提示原因，不记录当日签到，也不消耗模型用量。应在数据包中提供覆盖早中晚期、不同总价值的奖励包；只配置大量高价值补给时，早期玩家可能找不到合格包。冷启动没有观测上限，依靠阶段约束及池中最低价值包，因此奖励池应包含合理的新手补给。

提交前再次读取当前条件、进度与候选，并校验目录版本和日期。当天已有记录时返回原奖励，不重新抽取。奖励入账后使用既有系统空间领取机制；后续修改目录或估值不会改写已获得的权益。

## 阶段与其他信号扩展

在 NeoForge 游戏事件总线上监听 `PlayerProgressionEvent`，可以根据服务端权威阶段调用：

```java
event.calibrate(1.0, stageMinimum, stageMaximum);
```

`player()` 提供当前玩家，`observed()` 是未经校准的分位数，`samples()` 是有效变体数。`calibrate(scale, minimum, maximum)` 应用轻度比例修正和阶段上下界；多个监听器的上下界取交集、修正系数相乘。无效或冲突的边界会报错，不会回退为无限制。

当前只提供这一个复用入口，未绑定 GameStages / ProgressiveStages，也未收集合成或探索广度统计。整合包或兼容模组可在确认阶段 API 后接入，不需要改动签到工作流；其他本地业务也可在服务端游戏线程调用 `PlayerProgression.estimate(player, settings)`。

## 状态与持久化

离线签到状态卡显示评估方式、分位数、样本数、置信等级和优先价值区间；样本不足时显示冷启动说明。未签到且没有候选时提示补充奖励包或估值。

玩家活动数据最多保存 32 天完整奖励快照，较早记录归档到 `<存档>/system/signin/<UUID>/<绑定代次>/<年份>/<日期>.dat`，使用压缩 NBT。每日去重和历史领取都能读取归档。撤销系统会删除该玩家的签到归档；清空聊天记忆不会删除签到权益。

## 连续、累计与固定规则

`server.rules` 为可选对象，默认无固定轮换、无自定义里程碑；内置模块另外提供首次、累计七日及连续七日奖励。签到成功后显示计数与里程碑进度，`/signin_status` 可随时查看，不执行签到。

```json
{
  "server": {
    "type": "system:signin",
    "rewards": ["system:food", "system:mining"],
    "rules": {
      "daily_cycle": ["system:food", "system:mining"],
      "milestones": [
        {
          "id": "example:weekly_three",
          "metric": "week",
          "target": 3,
          "reward": {
            "label": "example.reward.weekly_three",
            "contents": [{ "content": { "type": "system:currency", "currency": "system:coin" }, "amount": 3 }]
          }
        }
      ]
    }
  },
  "client": "system:signin"
}
```

| `rules` 字段 | 类型 | 默认值 | 说明 |
| --- | --- | --- | --- |
| `daily_cycle` | 奖励 ID 数组，最多 366 项 | 空 | 第 N 次成功签到使用 `(N-1) % 数组长度`，漏签不跳过位置；失败不推进，不自动改选其他奖励 |
| `milestones` | 数组，最多 128 项 | 空 | 达到阈值时保存一次奖励权益；随后从 `/records` 领取到空间 |
| `milestones[].id` | Identifier | 必填 | 同一模块定义内唯一的稳定 ID |
| `milestones[].metric` | `total` / `streak` / `week` / `month` | 必填 | 分别为累计、连续、本周、本月成功签到天数 |
| `milestones[].target` | 正整数 | 必填 | 周目标不得超过 7，月目标不得超过 31 |
| `milestones[].reward` | Reward | 必填 | 支持物品、系统币、经验与可信 action |

固定奖励仍必须属于模块允许的签到奖励目录且条件成立。配置空 `daily_cycle` 保留原本的离线 Evaluate / AI 选择流程。多个签到配置共用每日去重与计数，但执行所选模块自己的规则；里程碑以模块实例 ID、里程碑 ID 和周期共同确定身份。

累计天数永久增加；中断一天后下一次签到的连续天数从 1 开始，历史最长连续天数保留。周一开始新一周，自然月第一天开始新月；`total`／`streak` 里程碑终生一次，`week`／`month` 每个对应周期可以再领一次。暂不提供补签。

时区统一使用服务端 `timeZone`，按自然日期而非 24 小时计时。保存日期高水位，时钟回退不能在更早日期新增签到；已有日期返回原奖励。改变时区保留累计／最长连续，下次新日期签到重置连续和周月计数，同日不会因改时区重复领取。客户端状态卡使用服务端传来的时区，避免两端设置不同导致计数不一致。

计数在升级后的新签到中开始累计，不扫描归档推算旧签到总数或补发旧里程碑；原有每日快照与唯一记录继续有效。每日奖励、计数、新事实和里程碑快照在同一玩家事务中保存，写入失败不推进任一状态。已达成权益保留快照，不因后续改定义被替换；见[进度与奖励](progress-rewards.md)。
