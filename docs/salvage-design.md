# 装备分解设计稿

状态：首版已接入（2026-11-17，`master` / Minecraft 26.1.2）。本文保留设计推导与后续方向；实际数据格式、扩展接口、默认规则、数量限制及核对指令以[装备分解](salvage.md)为准。已执行编译与静态校验，未启动游戏验收。

## 定位与首版范围

分解归入现有 `system:workshop`，与维修共享入口，适用于武器、工具、护甲及数据包明确允许的其他物品。规则匹配实际 ItemStack，不在 Java 中枚举“剑／斧／模组武器”类别。维修保留现有语义；固定物品收购继续归商城。

首版流程是：主手持有一件装备 → 查询分解方案 → 展示完整消耗与确定产出 → 玩家确认 → 消耗该件装备 → 产出存入系统空间。一次只处理一件、数量为 1 的物品堆，不扫描或批量清理背包，不取下玩家身上的装备。

| 能力 | 首版设计 | 说明 |
| --- | --- | --- |
| 固定返材 | 支持 | 例如铁剑拆成铁粒；具体物品和数量由数据包指定 |
| 耐久影响数量 | 支持 | 用剩余耐久比例参与数量公式，也可完全不考虑耐久 |
| 按价值转材料／系统币 | 支持 | Evaluate 提供单件价值，规则明确换算率及产物 |
| 附魔影响数量 | 支持基本公式 | 提供原生附魔数量／等级总和；默认不增加返材，不猜测模组词条价值 |
| 条件与额外费用 | 支持 | 玩家条件复用现有 EntryConditions，费用复用 Saturn Cost |
| 自动逆推合成材料 | 后续 | 多配方、替代材料、副产物和机器配方无法可靠还原实际投入 |
| 提取附魔书／词条 | 后续 | 需要独立的组件读取与产物构造策略，不能只调整数量 |
| 批量分解／自动分解 | 后续 | 需要选中列表、逐件快照及部分成功语义 |
| 随机返材／稀有副产物 | 后续 | 需要在确认后冻结随机结果，并处理反复报价挑选结果的问题 |
| 强化、重铸、品质升级 | 另行设计 | 可以沿用工坊入口及订单经验，不在首版预建完整加工框架 |

## 数据包与模块

新增仅服务端加载的原生数据包注册表 `system:salvage_rule`，条目路径为 `data/<namespace>/system/salvage_rule/<path>.json`，tag 路径为 `data/<namespace>/tags/system/salvage_rule/<path>.json`。客户端只接收主手及方案快照，不同步整张规则表。

`WorkshopSystemModule` 增加可选 `salvage`，支持 ID、`#tag` 或混合数组。省略／空数组表示不提供分解，保留旧工坊配置的行为；当前 `costs` 仍是维修费用，分解费用在每条规则内声明。

```json
{
  "order": 45,
  "icon": { "id": "minecraft:anvil" },
  "server": {
    "type": "system:workshop",
    "costs": [
      { "type": "system:currency", "currency": "system:coin", "amount": 1 }
    ],
    "salvage": "#example:equipment"
  },
  "client": "system:workshop"
}
```

查询与确认均按当前工作流所属模块实例核对允许的规则；不能借用另一份工坊配置的规则或权限。可让 WorkshopSystemModule 实现已有 `CatalogModule<SalvageRule>` 表达该目录，不新增同质服务端模块类型。

## 规则示例：铁剑返材

文件：`data/example/system/salvage_rule/iron_sword.json`。

```json
{
  "label": "example.salvage.iron_sword",
  "priority": 100,
  "input": { "items": ["minecraft:iron_sword"] },
  "costs": [],
  "outputs": [
    {
      "content": {
        "type": "system:item",
        "item": { "id": "minecraft:iron_nugget" }
      },
      "amount": "floor(18 * salvage_durability)"
    }
  ]
}
```

此例满耐久返 18 个铁粒，50% 耐久返 9 个。这是配置示例，不代表通用平衡值。用 `"amount": 9` 即可不考虑耐久、固定返 9 个。附魔和自定义名字不会被复制到铁粒上，确认卡片需明确展示装备将整体消耗。

| 字段 | 类型／默认值 | 语义 |
| --- | --- | --- |
| `label` | 文本组件，必填 | 字符串按现有约定作为翻译键 |
| `input` | 原版 ItemPredicate，必填 | 匹配真实物品、tag 及组件，复用图鉴已经采用的谓词体系 |
| `priority` | int，默认 0 | 越大越优先；同值按完整规则 ID 排序 |
| `outputs` | 1～36 项动态产出，必填 | 每项使用现有 SpaceContent 与一个数量提供器 |
| `outputs[].content` | SpaceContent，必填 | 复用物品、系统币、经验或已注册扩展类型的分派 |
| `outputs[].amount` | Saturn NumberProvider，默认 1 | 常数、公式或已有数字提供器；报价时求值并冻结 |
| `costs` | Saturn Cost 数组，默认 `[]` | 消耗装备之外的费用；显式空数组免费 |
| `enabled` | boolean，默认 true | 关闭后不再生成新方案 |
| `display_condition` / `condition` | EntryConditions | 分别控制可见与可执行，服务端复核 |

这里不再给结果增加 `fixed`、`value` 等一层分派：两者只在数量计算上不同，SpaceContent 已能分派内容类型。新增的动态产出定义可使用 `SalvageOutput(SpaceContent content, NumberProvider amount)`；求值后转为现有 `SpaceStack` 和 `Reward`，复用奖励预览与交付。固定物品模板的 count 必须为 1，实际数量只由 amount 决定。

附加 action 沿用既有奖励语义：在空间兑现时执行，不在销毁装备过程中直接执行。它的 amount 表示执行次数，规则作者应显式配置，系统不会按价值自动放大。

## 数量上下文与 Evaluate

下列 `salvage_*` 名称是拟新增的、仅当前报价可用的数字变量，不是 Saturn 当前已经提供的全局变量。实现时通过经核对的数字上下文扩展接口注入，不用字符串替换表达式，也不修改玩家全局属性。

| 变量 | 含义 |
| --- | --- |
| `salvage_durability` | 剩余耐久比例，0～1；无耐久物品为 1 |
| `salvage_damage` | 已损耗耐久，无耐久物品为 0 |
| `salvage_max_damage` | 最大耐久，无耐久物品为 0 |
| `salvage_enchantment_count` | 原生附魔条目数，不含模组自行保存的词条 |
| `salvage_enchantment_levels` | 原生附魔等级总和，包含诅咒，未经价值加权；不默认用于任何增益 |
| `salvage_value` | Evaluate 对实际 ItemStack 查询得到的单件价值，未知时不可读取 |

例如把允许的装备折为“8 点价值一枚碎片，回收率 25%”：

```json
{
  "content": {
    "type": "system:item",
    "item": { "id": "example:equipment_scrap" }
  },
  "amount": "floor(salvage_value * 0.25 / 8)"
}
```

`example:equipment_scrap` 仅为整合包物品占位，System 不因此注册一套材料。多个产出可各自配置公式，但配置者必须考虑总价值，不能让每项都独占同一份完整回收预算。

Evaluate 结果按报价中的实际物品及组件查询一次。使用价值变量但估值未知时拒绝该方案，不能按 0 或猜测值继续；固定数量和仅耐久公式仍可使用。Evaluate 不是材料组成 API，因此价值方案只产出明确配置的碎片、材料或货币，不会自行把未知武器拆成钻石或下界合金。

耐久折损不自动叠加在 Evaluate 结果上；需要时显式写入公式，避免估值提供方已经考虑耐久后再次折损。P90 用于出售解锁／玩家进度，不限制玩家处理自己已经持有的装备。回收率、兑换单位及与维修／商店的循环收益由数据包协调，系统不承诺跨所有模组的自动经济平衡。

数量统一向下取整，0 项省略；负数、非有限数、溢出、未知变量或无法构造的产物直接拒绝报价。所有产出均为 0 时提示“当前装备无法回收材料”，不生成销毁按钮。相同内容可按现有合并规则合计，求和仍检查溢出。

## 多条规则与目标保护

1. 先按模块允许项、enabled、输入匹配及展示条件收集候选。
2. 按 priority 降序、完整 ID 升序选定唯一规则，不叠加其他规则的产出。
3. 核验该规则的执行条件与费用。不满足时展示限制，不悄悄回退到低优先级规则绕过限制。
4. 方案记录规则 ID、模块实例、定义版本、输入完整组件快照及所有已求值数量。

高优先级规则可以专门处理特殊组件装备，低优先级规则覆盖普通装备。固定材料方案和通用价值方案因此可以并存，不需要建立第二套目录合并服务。

首版只读取主手所选栏位，要求 count 为 1。已知非空容器内容（如原版容器／收纳袋组件）默认拒绝；第三方内部库存、绑定、任务物品与特殊耐久等语义由扩展检查处理，不能声称原版组件检查涵盖全部模组。

预留服务端 `SalvageCheckEvent`：提供玩家、规则身份与只读输入快照，允许其他模组用 Failure 拒绝操作；报价和确认均调用。不允许该事件直接修改背包或写产物，变更计算逻辑应通过规则或 NumberProvider 扩展完成。

## 玩家交互与 Agent

工坊增加“分解主手装备”，系统界面内 `/salvage`、`/分解` 进入同一报价流程。语音“分解手上的武器”也只打开方案，不直接销毁。

报价卡片显示原装备及完整 tooltip、所用规则、消耗数量、费用、确定返材与“确认分解／取消”。耐久与附魔影响已体现在确定数量中，不用模糊的“预计可得”代替真实条款。成功后显示订单与“查看系统空间”；产出不要求背包有空位，但要先预留空间账本容量。

报价暂定两分钟有效，同玩家新方案替换旧方案。切槽、替换物品、数量／耐久／组件变化、规则重载、模块权限变化均使未执行报价失效。确认既核对完整快照，也核对本次连接内的实际目标引用，保持现有维修的目标保护。

拟议动作与工具为 `system:salvage_quote` / `game.salvage.quote`、`system:salvage_confirm` / `game.salvage.confirm`。报价只读，离线可用；确认消耗一次写额度，不允许事件自动执行。自由模式和扩展兜底可查询／展示方案，但确认不进入模型可调用目录，必须由玩家对当前卡片明确点击或使用已有语音按钮确认链路，服务端按调用来源及报价凭证核验，不能只靠提示词约束。

这些业务指令不导出到游戏 `/system` 指令树。管理员订单核对属于另一个管理入口。

## 持久化与失败语义

新增 `WorkshopDataStorage` 保存分解订单，继续使用玩家业务 NBT、private 字段、copy 与 markDirty。临时报价仅由工坊运行时保存，实际 ItemStack 引用不序列化。订单保存订单／报价 ID、模块和规则、绑定代次、输入快照、冻结费用、冻结 Reward、状态及审计信息，状态使用 enum。

不把分解伪装成商品订单或给 AgentEngine 添加业务字段。复用 CommerceCosts、系统空间、Agent 日志和既有归档思路；如果后来需要共用事务工具，只提取已重复的实际步骤。

| 状态 | 含义及恢复 |
| --- | --- |
| `PREPARED` | 已保存条款并预留空间，尚未允许触碰游戏数据；重启时可安全取消 |
| `EXECUTING` | 已持久化即将执行消耗，游戏效果可能发生；重启后转 `UNKNOWN`，不再次扣物品 |
| `COMPLETED` | 已确认游戏线程执行成功，空间权益与成功标记在同一次玩家事务保存 |
| `FAILED` | 已证明没有发生游戏副作用的失败；释放占位 |
| `UNKNOWN` | 部分付款、消耗结果或跨文件持久化不能确定；保留快照，锁定产出等待核对 |

建议执行顺序：

1. 存储线程以报价 ID 唯一创建 `PREPARED` 订单及不可领取的空间占位。重复点击返回同一订单，不能创建第二份。
2. 存储线程持久化 `EXECUTING`，成功后才进入游戏线程。
3. 游戏线程复核玩家、权限、目标、规则版本及费用可付性，消费临时报价。费用视图排除目标栏位，避免装备既充当费用又被分解。
4. 在同一游戏线程操作内支付额外费用，付款后再次核对目标，再移除确切的那件装备；执行中不等待文件 I/O。已发生部分副作用的错误返回不确定结果，不假装整体回滚成功。
5. 确认成功后，存储线程在一次玩家事务中将订单标记 `COMPLETED`，把 `salvage:<订单ID>` 权益变为可用并入库；重试只补同一份结算，不再次操作背包。

产出与费用一旦成为持久条款便不得重新求值。首版产出只接受确定性的常数、公式及数字提供器；实现时验证可用提供器及变量，未知扩展需显式声明支持此上下文。随机提供器及随机变量不开放，避免用反复报价挑选高返材结果。

不可逆操作成功后的收尾不因关闭页面、聊天取消或断线而丢弃，仍在后台完成；但要核验绑定代次，不能在撤销／重新绑定后向新账本写入旧订单。正常进程内的暂时落盘失败保留执行回执并重试结算。

MC 玩家背包与 System 玩家 NBT 是两份持久数据。仅保存订单和输入快照无法证明崩溃／回档时装备是否已经永久扣除，也不能通过“背包里少了一把相同剑”推断；因此不承诺跨文件的严格原子提交。启动时 `UNKNOWN` 只能冻结，不能自动补发输入、重扣输入或开放输出。

拟议管理员 `/system workshop list/show/resolve` 参考现有 commerce 核对入口。`consumed` 只解锁原冻结产出，`not_consumed` 只关闭订单；都不再次扣物品或自动退费用，并保存核对人与理由。已开放或部分领取的权益不能反复改判。订单历史分页、有界读取；未结清订单不因历史清理被删除，达到活动账本上限时拒绝新操作。

成功结算可以在同一事务记录 `system:salvaged` 可信事实：来源为规则 ID、对象为输入物品 ID、occurrence 为订单 ID，供现有进度奖励系统使用。失败或未知不记录成功事实，客户端／AI 不能上报分解成功。

## 代码职责与实施顺序

| 位置 | 建议内容 |
| --- | --- |
| `data.catalog` | SalvageRule 与动态产出 Codec、输入与参数校验 |
| `data.store` | 分解订单快照与状态枚举 |
| `assistant.workshop` | 匹配、数字上下文、报价、主手消耗、订单结算及恢复 |
| `module.builtin.workshop` | 报价／确认工作流与路由 |
| `module.builtin.storage` | WorkshopDataStorage，直接拥有所有持久订单数据 |
| `module.builtin.WorkshopSystemModule` | 规则选择、存储与生命周期声明 |
| `data.output` / `assets/system/cards` | 报价与回执，复用物品、费用和奖励控件 |

先实现固定输出与完整订单链路，再接耐久／Evaluate 数量上下文及扩展检查。两步共用同一种规则和产出格式。登记注册表、双语文案、卡片编辑器模板、docs 与默认数据时一起完成，不先留下只能由工具调用的半成品入口。

后续实现需验证完整组件目标失效、重复点击、未知估值、零产出、空间不足、额外费用部分失败、确认中断线／撤销、重载失效和未知订单恢复。首版现已实现并通过编译与资源静态校验；这些运行时场景尚未启动游戏验收。
