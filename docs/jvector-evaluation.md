# JVector 任务知识索引评估

评估日期：2026-10-30。对象为 `io.github.jbellis:jvector:4.0.2`，同时核对 3.0.6 的发布物；没有修改业务代码、依赖或当前存储格式。本次下载并读取 Maven 发布的 POM、JAR、sources，以及固定版本官方文档；实际测量的是文件大小，性能结论来自源码分析。未执行测试、性能基准或 Minecraft 进程。

本文的当前实现分析保留评估时基线。后续已按用户决定暂缓 JVector，并将本地存储整理为 [共享 / 玩家独立数据库](databases.md)，静态文本缓存与重载逻辑也已调整；下文 QuestKnowledgeCache 名称及逐次全文快照开销不再代表最新实现。

## 结论

JVector 可以在进程内保存和查询向量图索引，体积符合目前 10,000,000 字节的分发目标。它适合成为以后可替换的向量检索后端，但当前稀疏 TF-IDF 说明书索引直接迁移没有已证实的性能收益。

当前优先事项是缓存静态任务文档、持久化编码结果并改进稀疏检索。将来有较大规模的固定维度向量时，再比较 JVector 与精确检索。JVector 自身不生成文本 embedding，也不会因为换索引就提高同义句理解能力或减少模型调用。

## 它负责保存什么

官方 `OnDiskGraphIndex` 提供 load / write；磁盘 writer 保存图结构、节点编号、层次以及配置的浮点向量 / PQ / NVQ 等特征。因此可以持久化已构建索引，重启时加载，减少重新建图。

应用仍需自行保存标题、章节、正文、段落边界，以及节点编号到任务 ID 的对应关系。编码器版本、词表或哈希参数、IDF、语料指纹也必须一起保存。JVector 的图文件不能直接替代目前的 JSON 文档，也不替代 FTB 任务定义、玩家进度或领奖记录。

可采用以下逻辑分工，尚未实施：

- 文档：原文和语言，由当前文档层管理。
- 编码：将文档 / 查询变成相同空间的向量。
- 索引：JVector 管理近邻图及向量存储。
- 元信息：保存段落和任务映射、编码参数、语料版本。
- 权限：查询时读取当前队伍权限，结果返回前再次检查 FTB。

更新时应先写完整的新一代文件，完成后切换元信息入口，避免正文、节点映射和图来自不同代次。旧索引及 reader 的关闭由模块生命周期负责；Windows 下还需验证文件映射与替换时的句柄释放。

## 与当前 TF-IDF 的适配

现有 LexicalIndex 使用 `Map<String, Double>` 存稀疏特征，特征空间随语料变化。JVector 常规向量路径使用固定维度的 VectorFloat 和数值相似度，不能直接传入这些 Map。

有三种方向：

| 方向 | 分发 / API 成本 | 代价 |
| --- | --- | --- |
| 将整个词表展开为浮点数组 | 无模型、无 API | 词表大时非常浪费空间；IDF 变化会使已有向量过期 |
| 固定维度特征哈希，例如 512 / 1024 / 2048 维 | 无模型、无 API | 需要保存哈希算法 / seed / IDF，碰撞可能损害专有名词区分，不能视为语义模型 |
| 真正的文本 embedding | 取决于本地模型或外部 API | JVector 可以消费结果，但不负责模型体积、调用费用或首次生成成本 |

BuildScoreProvider / SearchScoreProvider 允许自定义打分，并非所有用法都强制采用标准稠密相似度。但沿用稀疏打分仍要适配构图、质心 / 查询接口并自行管理稀疏向量持久化；不能靠这一扩展点直接获得现成稀疏数据库。对于大量互不重叠的稀疏词项，近邻图的导航效果同样需要验证。

若使用标准 COSINE，源码中的返回值为 `(1 + cosine) / 2`；DOT_PRODUCT 对单位向量也进行相同映射。目前原始余弦阈值 0.08 不能直接原样使用；对应的变换分数是 0.54。查询特征覆盖率阈值 0.25 也仍需应用自行计算，不能被近邻分数替代。推荐保留原始特征，对候选做原始打分复排。

## 性能与内存判断

当前检索主要包含：

1. FtbQuestGuideTool 在服务端线程遍历候选任务，重新解析本地化标题、章节、正文并检查权限。
2. QuestKnowledgeCache 串行执行整个 search，比较完整文档快照；首次或变化时分段、编码、建索引，必要时保存文件。
3. LexicalIndex 遍历所有段落，按查询特征计算分数，并对结果排序，之后按可读 ID 筛选、按任务去重。
4. 返回服务端线程，复核来源、权限和正文。

JVector 主要可能改善第 3 步，持久化图和向量也能减少第 2 步重建；它不能自动消除第 1 步逐次读取全文、完整快照比较或外层 synchronized 的串行化。

已知用户整合包包含 837 个任务，但这不是说明书文档数，更不是分段后的向量数。目前没有实际生成的知识缓存可用于测量真实段落数，不将 837 直接当作索引规模。对几百至几千个段落，精确稀疏扫描 / 倒排检索可能已经足够，建图、转换和磁盘访问成本未必划算。达到几万至几十万个固定维度向量时，ANN 更值得比较；这不是已经测得的性能分界。

未压缩 float32 向量的原始占用是 `向量数 × 维度 × 4`，不包含图、对象、元信息、建索引临时内存或文件缓存：

| 向量数 | 384 维 | 1024 维 |
| ---: | ---: | ---: |
| 1,000 | 1.46 MiB | 3.91 MiB |
| 10,000 | 14.65 MiB | 39.06 MiB |
| 100,000 | 146.48 MiB | 390.63 MiB |

若直接展开 20,000 个 TF-IDF 词项，1,000 个向量就需要 80,000,000 字节的原始数值存储。磁盘索引能改变常驻内存和 I/O 分布，不能让所有这些数据与图开销凭空消失。PQ / NVQ 可进一步压缩，但小语料不宜直接增加训练与调参复杂度。

没有在本项目上测得 JVector 的 QPS、P95/P99 或召回率；官方大数据集基准和 SIMD 图表不能代替当前任务语料、Windows / Java 21 默认启动环境下的结果，也不保证所有图查询都是严格对数复杂度。

## 接入时要保留的行为

- 单节点代表一个段落，静态映射到语言与任务 ID。同一任务多个段落命中时去重，不能只取五个段落就假设有五个任务。
- GraphSearcher 的搜索缓冲区有状态，不可作为全局单例并发使用；索引可共享，每个并发查询需要独立 searcher / view 或明确的借用管理。
- 搜索 API 接受 Bits / acceptOrds，可按当前玩家允许读取的任务映射到段落掩码。它是结果过滤，不应假设图遍历完全不经过其他节点；禁止返回未授权的标题、片段和正文。
- 掩码高度稀疏时需扩展候选数或回退精确检索；后台完成后仍进行 FTB 原生权限复核。ANN 的近似结果不能成为授权或“确实没有文档”的证明。
- TF-IDF 的 IDF 依赖整份语料。即使图支持节点变更，编辑一篇文档也可能改变其他向量；不能直接宣称可免费局部更新。
- 当前 build.gradle 使用 `configurations.jarJar.singleFile` 只展开 exp4j。增加新的 JarJar 依赖前必须调整该开发运行处理，处理传递依赖、模块归属和 Multi-Release 资源；不能只加一行依赖就认为集成完成。
- 低相关度时保留未找到 / 现有模型路由行为，不因使用 ANN 放宽阈值或自动授权执行任务。

## 建议顺序与后续测量

先把当前文档快照按语言缓存，FTB 重载或已确认的任务编辑事件更新静态内容；每次查询只计算权限集并复核返回项。事件无法保证覆盖的改动需要低频指纹检查。然后比较持久化稀疏特征、倒排候选、只对候选取 Top-K 与当前全量扫描。这样保留原始词项信息，不增加哈希碰撞、ANN 漏召回或分发依赖。

如果之后引入固定维度编码器，或真实语料扩大到精确检索明显占用预算，再实现一个独立 JVector 后端。标准编码可先比较特征哈希与精确稀疏检索，保持词项精确复排；不要为了使用图索引强行增加 embedding API。

用户明确要求测试后，再用相同语料比较：首次 / 重启索引加载、热查询 P50 / P95 / P99、同编码空间的 Recall@5、玩家权限过滤后的召回、真实问题的相关性、索引文件大小、常驻及构建峰值内存、CPU、实际发布 JAR 字节数。小规模和扩大语料分别记录，默认 JVM 与 SIMD 启动参数分开。当前基线、哈希后精确搜索、哈希加 JVector 应分开比较，以区分编码损失和 ANN 损失。
